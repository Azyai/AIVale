# 05 数据库与一致性开发规范

## 1. 适用范围与当前基线

本文约束 AIVale 现有数据层及后续 Agent 数据实现。表字段、引入阶段和迁移批次以已确认开发计划第 5 章为准；本文规定实现方法，不另建数据字典，不表示计划中的表已创建。

| 范围 | 当前实现与开发约束 |
| --- | --- |
| 主数据库 | `model/main.go` 通过 `SQL_DSN` 选择 SQLite、MySQL 或 PostgreSQL；`model.DB` 保存业务事实 |
| 日志数据库 | 未配置 `LOG_SQL_DSN` 时复用主库，否则使用独立 `model.LOG_DB`；日志库另支持 ClickHouse |
| 持久化与迁移 | 使用 GORM，现有启动链包含 `migrateDB`、`AutoMigrate` 和显式迁移函数；常规迁移由主节点执行，但应逐项检查实际启动前置操作 |
| Agent 数据边界 | `AgentScope`仍是内部值对象；P01-T01在`model/agent_workspace.go`实现`ag_workspaces`、`ag_workspace_members`及基础仓储，P01-T04另为真实写操作前移幂等/outbox两表，其余规划表继续按阶段实现；持久化不证明动作授权 |
| 缓存 | Redis 和进程缓存用于加速、唤醒和可重建投影，不作为 Run、权限撤销或费用的唯一事实源 |

不得把其他项目的 Flyway、MyBatis、自动代码生成或“生产禁止所有启动迁移”直接写成本项目现状。调整迁移执行方式须作为独立设计与实现任务，不能只修改规范即视为落地。

仓库兼容范围为 SQLite、MySQL ≥ 5.7.8、PostgreSQL ≥ 9.6。已确认计划 §1.6 将 **P00-T03** 限定为真实 MySQL 验证；该任务例外不等于删除其他方言支持，也不能外推为后续迁移已满足验证要求。后续任务按明确用户范围和适用仓库约定确定矩阵，结论只覆盖实际执行的引擎及版本。

## 2. 数据所有权与模型边界

1. 继续复用现有用户、Team、模型 Token、渠道、价格、订阅和钱包。Agent 不建立第二套身份、余额或模型定价事实。
2. `team_id` 是租户与账务归属，`workspace_id` 是其下的资源范围。业务服务先完成身份、成员和对象授权，再把服务端解析的范围传给数据层；客户端字段和 `AgentScope` 的存在均不能替代授权。
3. 新增 Workspace 资源的列表、详情、变更、导出、下载、SSE 和后台执行查询必须带正确范围。创建子资源时，在事务中核对父子对象的 Team、Workspace 及状态。
4. GORM 模型负责持久化映射，不直接作为对外响应。DTO 集中处理 ID 字符串、时间单位、空值、字段隐藏及固定错误契约，规则见 [架构与编码](04-architecture.md)。
5. Agent、Skill、Workflow 发布版本不可覆盖；回滚切换发布指针或创建新版本。历史 Run 继续引用原版本，禁止通过修改旧版本改变已发生运行的含义。
6. 逻辑引用首期通过服务层事务校验、唯一约束、删除前引用检查及离线孤儿检查维护；不引入跨旧表、跨主日志库的级联删除。

规划表按职责分组，不为补齐目录提前创建空表：

| 职责 | 规划表及边界 |
| --- | --- |
| 资源与授权 | `ag_workspaces`、`ag_workspace_members`、`ag_token_grants`；仅拥有新域的授权关系 |
| 定义与发布 | `ag_agents`、`ag_agent_versions`、Skill/Workflow 定义、版本及绑定表；发布内容固定 |
| 执行与可靠性 | `ag_runs`、`ag_run_steps`、`ag_run_events`、`ag_idempotency_keys`、`ag_outbox`、审批与检查点表 |
| 费用关联 | `ag_gateway_calls`、`ag_usage_items`、`ag_budget_reservations`；关联网关结算，不另扣钱包 |
| 外部能力与文件 | 凭据、MCP、Artifact、会话消息及调度表；字节与秘密按受控存储规则处理 |

## 3. 类型、命名与可解释性

| 项目 | 必须遵守的规则 |
| --- | --- |
| 表与索引 | Agent 表显式指定 `ag_*` 表名；索引名最长 55 字符，不依赖 GORM 默认复数猜测名称 |
| 主键与引用 | 新表使用有符号 int64，主键由 GORM 机制生成；引用旧表按其实际类型校验边界，不能直接窄化转换 |
| 对外 ID | 规范正十进制字符串，范围 `1..9223372036854775807`；拒绝 0、符号、前导零、空白、指数、数字 JSON 和溢出 |
| 额度 | 存储为有符号 int64，沿用平台 quota 单位；对外为非负十进制字符串，禁止用浮点表示额度或做无边界转换 |
| 时间 | 新域统一 UTC Unix 毫秒 int64；旧表 Unix 秒保持语义，通过适配层显式转换 |
| JSON 数字 | 毫秒、`seq`、游标、`revision` 必须在 JavaScript 安全整数范围；`seq/revision` 至少 1，`after_seq` 至少 0 |
| 空值 | 未知时间、未关联对象和未知实际费用用 NULL；不能用 0 伪装有效对象或已确认费用，真实确认的零费用可以记录为 0 |
| 可变版本 | 按计划使用 `revision`，初值 1；持久化条件检查后成功加 1，不自动为只追加表套用可变字段组 |
| 文本与 JSON | 采用跨库 TEXT；经 `common.Marshal/Unmarshal` 等统一封装，校验 schema 版本与 UTF-8 字节上限 |
| 默认值 | 计划标记“服务赋值”的字段由应用显式设置；TEXT 不依赖 MySQL 5.7 不支持的默认值 |
| 归档 | 显式状态与 `archived_at`，不依赖 GORM 隐式软删除；归档后 slug 不自动回收 |

- slug 先统一为小写 ASCII，再入库校验；不能让三库排序规则决定业务唯一性。长 MCP 工具名按计划另存名称摘要参与唯一索引。
- 默认单个 TEXT 上限为 60 KiB，事件载荷 16 KiB，单段指令 32 KiB，凭据密文 16 KiB；配置不得超过列的安全上限。较大内容转受控 Artifact，数据库只存元数据、存储键和摘要。
- 每个新增或变更的模型、字段应写清中文业务说明：所属实体、单位、合法状态、NULL 含义、敏感等级和引用对象。金额、时间与版本字段不得只有缩写名称。
- 数据字典与 GORM 映射同步；数据库表/列注释按引擎能力维护，SQLite 等无同等注释机制时由模型及数据字典保留说明，不能为了注释破坏跨库迁移。

## 4. GORM 查询与方言规则

1. 优先使用 GORM 的 `Where/Select/Find/Create/Updates` 等现有能力。所有动态值参数化；排序字段、列名和操作符来自服务端允许列表，不能拼接客户端输入。
2. 更新必须显式列出可写字段；不能把请求体无差别映射到模型。需要写入 `false`、`0`、空值时明确选择更新列或映射，验证 GORM 的零值行为，避免“已成功但未保存”。
3. 事务中的读写使用同一 `tx`，不得夹用全局 `DB` 绕开事务。所有写入检查 `.Error`；条件更新和删除还要检查 `RowsAffected`，0 行不是成功。
4. 标准行锁使用 `model/locking.go` 的 `lockForUpdate(tx)`；禁止旧式 `Set("gorm:query_option", "FOR UPDATE")`。SQLite 不执行 `FOR UPDATE`，仍须使用条件更新、事务和有界冲突重试保障竞争正确性。
5. 必须使用原生 SQL 时，区分主库与日志库的方言。复用 `common.UsingMainDatabase`、`common.UsingLogDatabase` 及保留字/布尔辅助表达，不凭主库类型推断日志库类型。
6. 不依赖 MySQL 专属函数、PostgreSQL JSONB/部分索引或 MySQL 8 `SKIP LOCKED` 实现共用能力。跨库替代方案须真实验证，SQLite 结构变更可能需要受控重建。
7. 不使用会导致反复迁移的 GORM 布尔默认标签来代替应用默认值；修改驱动或 GORM 时按兼容版本组评估，检查重启是否反复 ALTER。

## 5. 事务、并发与幂等

事务保持短小，不在持锁期间请求模型、调用工具、等待审批或上传对象。并发语义在数据库层闭合，Redis 锁和进程互斥不能替代唯一约束、版本条件及提交检查。

| 操作 | 同一事务的最小一致性边界 |
| --- | --- |
| P01 授权变更 | 授权对象、父子归属与状态校验、幂等结果 |
| P02 发布 | 草稿版本比较、不可变版本及阶段内绑定、发布指针、幂等结果；该阶段不依赖尚未实现的 outbox |
| P03 创建 Run | 幂等受理、固定版本、Run、首个 `run.queued` 事件、适用消息及 `run_ready` outbox；提交后才返回已受理 |
| 领取 Run | Workspace 槽位、合法状态、租约与 `lease_epoch`、对应事件；只有一个竞争者成功 |
| 预留预算 | 校验状态与限额，写 reservation/step，原子修改 reserved 和次数；不扣 Team 钱包 |
| 结算投影 | 来源事件唯一去重、reservation 状态迁移、用量事实与 Run 汇总；重复消息不能重复计数 |
| 审批决策 | 决策 CAS、过期/取消/版本检查、恢复状态、outbox 与必要审计 |
| 调度触发 | fire 唯一键、下一次触发时刻、Run 与 outbox；同一触发不产生多个 Run |

- 资源编辑使用“归属 + 预期 revision + 合法状态”的条件更新，成功后版本加 1；发布草稿使用计划定义的 `draft_revision`，不能与资源基础信息的 revision 混用。
- 幂等唯一键为 `(scope_hash, key_hash)`。scope 包含工作区、主体和操作；请求摘要包含实际目标资源路径、有效身份、固定版本和规范化业务内容。同 Key 同请求返回原结果，同 Key 不同请求返回 409，不产生新副作用。
- 活跃操作的幂等记录不提前清理。受理幂等不等于外部执行幂等；遇请求结果未知，按 [Agent 执行规范](02-agent-runtime.md) 处置，不能重新发起收费或写操作。
- worker 每次接管递增 `lease_epoch`，其持久化写入均校验当前 epoch。租约保护本库写入，不能撤销已发往外部的请求。
- 竞争领取采用有界候选与条件更新，检查影响行数；锁顺序固定，死锁或忙冲突有界重试且重试前确认业务可安全重放。不得以无限重试掩盖失败。
- 槽位释放由明确状态迁移统一负责，避免成功、取消、超时各减一次。P10 子运行按计划先锁根 Run，再按固定顺序处理子 Run，根预算不得被并行子任务各自使用一遍。

## 6. 事件、Outbox 与费用事实

1. Run 事件以 `(run_id, seq)` 和 `(run_id, event_key)` 去重。短事务内校验 epoch、分配序号、追加事件并更新 `last_event_seq`；提交后广播，Redis 仅通知有新数据。
2. SSE 重连从主库按游标读取，按序输出并去重；事件已过保留期时给出明确过期错误和快照入口，不伪装成没有事件。
3. outbox 与相应业务变更同事务保存，至少一次投递；消费者凭业务唯一键去重。失败有次数上限、退避和 dead 状态，人工重投同一事件而不是创建新业务对象。
4. `ag_gateway_calls` 由受信 broker/网关写入，`(logical_call_id, attempt)` 与 `gateway_request_id` 唯一。相同调用键只查询既有状态，客户端或普通 worker 不能自报已结算。
5. `ag_usage_items` 是已确认结算的运行投影，来源事件唯一；修正用关联旧项的新行，禁止覆盖事实。Run 预算只是运行限制，不能再执行一次钱包预扣或结算。
6. 资金、Token 统计、独立日志库和调用账本并非天然单事务。日志 RequestId 非唯一收据，日志缺失不证明未扣费；不确定窗口保留 `unknown`/待核账状态，不能重新调用整段结算来“补齐”。
7. 未确认实际费用保留 NULL，不记 0 费用成功；未知预留不因 Run 终态或到期自动释放。真实费用高于预留仍记录真实值、停止后续调用并进入治理，不裁剪费用掩盖超额。

计费实现前完整阅读 `.agents/rules/billing.md`；表达式变更还需阅读 `pkg/billingexpr/expr.md`。本节定义数据边界，不替代既有计费规则。

## 7. 查询、索引与缓存

- 列表有分页上限并选择必要列，默认不读取输入、输出、凭据密文和大 JSON。批量加载关联摘要，禁止逐行查询造成 N+1。
- 索引与实际过滤和排序一起设计：Run 工作区历史、状态/可领取时间、状态/租约期限，事件 `(workspace_id, run_id, seq)` 等按计划建立并用代表性数据检查执行计划。
- 事件使用 `after_seq`，运行历史使用明确稳定排序；不能无限 OFFSET 或一次加载全部事件。文本搜索先采用允许的前缀/关键词范围，不为搜索绕过租户过滤。
- 缓存 key 包含租户、工作区及必要的角色/权限版本；保存、发布、归档和撤销后失效。安全关键调用读取有效授权或可证明最新的策略版本，不能仅依靠周期同步。
- 连接池使用现有 `SQL_MAX_IDLE_CONNS`、`SQL_MAX_OPEN_CONNS`、`SQL_MAX_LIFETIME` 配置，根据主/日志库容量与并发测量调整；不把最大连接数当作吞吐量保证。

## 8. 迁移与发布

1. 按计划 `DB-Pxx-xx` 设计批次，一次处理少量强相关表；编号是设计标识，不宣称已有同名迁移文件。模型、索引、应用默认、数据字典及迁移注册构成同一变更。
2. 新表显式命名并接入现有迁移链；仅有 AutoMigrate 不等于字段变更、回填和版本兼容已经安全。破坏性变更须写明确迁移逻辑，不能运行时按请求临时改表。
3. 在约定的真实数据库矩阵验证空库、代表性旧库升级及重复启动；核对实际列类型、NULL/默认、唯一约束、索引以及旧用户、Team、Token、余额和网关行为。
4. 共享结构演进采用 expand-contract：增加兼容字段 → 兼容读写 → 有界回填 → 校验 → 切换 → 后续独立版本移除旧字段。回填须有范围、进度、重试与中断恢复方式。
5. 迁移先行、业务能力后启用；API/worker 的就绪检查和默认关闭开关必须与数据库状态一致，不因表存在就开放未完成业务。
6. 回退优先关闭新入口、停止新任务领取并保留数据。禁止通过清库、删除客户表或回写历史事实完成应用回滚；正式恢复依赖已验证的备份方案。
7. 若触及独立日志库或共享驱动配置，覆盖对应日志库组合。不得将主库验证外推为 ClickHouse 日志路径通过，也不得仅凭 SQLite 单测声称其他方言兼容。

### 8.1 工作区首批持久化边界

P01-T01在现有主节点`migrateDB`的AutoMigrate列表追加工作区和成员两表，不新增跨旧表外键或级联删除。`CreateAgentWorkspace`/`CreateAgentWorkspaceMember`在传入的数据库上下文/事务上核对现有Team、启用用户及Team成员，成员创建同时核对工作区归属和active状态。现有Team没有活跃状态字段，不虚构该字段或改变旧Team模型。

六个基础仓储入口显式要求正数Team ID；列表有界且先带Team条件，成员查询还带Workspace条件。读取包括归档/blocked等元数据，供访问服务判断，不能直接当作可访问证明；用户离队后的残留行不通过清理延迟换取有效授权。每次访问的角色和身份判定由P01-T02服务负责。

slug先拒绝非ASCII再规范为小写，显示名允许重名；文本拒绝非法UTF-8和NUL，统一三库行为。描述最多4KiB；预算字段只存非负quota配置、默认值不高于最大值；策略先只接受`{"schema_version":1}`空配置，未来策略另行定义，不静默接受未实现安全字段。模型隐藏所有JSON字段，对外必须另建DTO。

数据库门禁使用`.agents/agent-platform/delivery/gate.py --profile workspace`及`database/matrix.py`；固定本地用例缺失不得放行。真实三库、fresh/upgrade、三次连接启动及原有团队保留按第07规范和工程入口README验证；发布最小投影与开发前Team投影分别记录来源，不将投影写成完整历史库。

### 8.2 工作区访问的实时事实

P01-T02新增`model/agent_workspace_access.go`只读查询，不新增列或迁移。它以一个SELECT关联启用且未软删除的User、有效UserSession及版本、当前TeamMember、Team、目标Workspace及可选显式成员行；Team来自当前关系，不接受请求声明覆盖。主体/会话失效与不可见资源用固定错误区分，数据库原始错误不返回客户端。

授权读取使用本次主库基础连接及Context，不使用User/Session/角色缓存、读副本或已开启事务的重复读快照。服务显式拒绝事务连接；后续写入的授权与锁定/事务一致性仍由对应业务任务实现。本次判定是单次事实快照，不保证撤销会中断已经开始的外部动作，也不能把返回的Scope用于下一次授权。

新增JOIN/状态过滤在三库真实运行；同一身份下一次查询须观察到退组、角色变更、成员删除/禁用、账号停用/软删除、会话撤销/过期或版本变化。该读路径仍回归已有迁移和旧数据保留，不把无schema变更当成无需数据库验证。

### 8.3 工作区列表与详情查询边界

P01-T03新增只读投影，不增表或列。列表先以当前管理会话、用户、Team归属、owner双事实或显式active工作区成员限制可见范围，合并名称筛选后执行COUNT，再按同一范围分页；详情也在查询中直接限制对象可见性，不先按裸ID加载再过滤。会话SID、会话/工作区/成员状态和角色采用各引擎的精确字符串比较，不能由MySQL默认大小写或尾空格等价规则放宽身份与权限。

名称`q`使用参数化、区分大小写的字面子串匹配：SQLite `instr`、MySQL二进制`LOCATE`、PostgreSQL `strpos`；百分号、下划线、感叹号及反斜线保持字面意义。排序只映射固定字段/方向，默认`created_at desc,id desc`；COUNT为零或偏移超出总量直接返回空页，不执行无意义的巨大OFFSET。查询次数有常数上限，禁止逐工作区重新查询造成N+1。

DAO显式选择元数据列，列表不选择description，不读取策略、预算、凭据或审计主体供前端使用；公开DTO另行选择字段并检查ID、毫秒时间和revision边界。工作区只读门禁使用`--profile workspace-read`，真实三库均须在同一组隔离目标上顺序完成迁移、访问判定、生产HTTP路由读取三阶段；结果要求见第07规范，不能由本节描述视为验证已经完成。

### 8.4 工作区写事务与审计事实

P01-T04提前建立计划内ag_idempotency_keys和ag_outbox，后续Token授权及运行投递复用，不因提前建表宣称相关阶段完成。创建、初始管理员、适用幂等完成收据和workspace_audit事件同主库事务，任一持久化失败全部回滚。创建在真实WorkspaceID生成后才保存完成收据，scope包含当前Team/主体/操作；不能用0表示不存在工作区。

写事务按User、Session、TeamMember、Team、Workspace、显式成员固定锁序校验当前事实，标准锁复用lockForUpdate；不在外部授权后按旧Scope裸写。编辑/归档条件包含Team、ID、合法状态及expected_revision，检查影响行数与安全整数上界。SQLite等竞争只能在确认回滚后有限重试整个操作，未知提交结果不能盲重发；不能依靠进程锁替代唯一约束和CAS。

归档不删除成员、slug或历史；活动计数大于零拒绝，损坏计数拒绝。当前没有运行/调度归档适配，元数据查询失败或出现ag_runs/ag_schedules/ag_schedule_fires等依赖表时关闭归档放行，待对应领域补真实停止触发和资源检查。

审计outbox只保存最小引用、主体、动作、revision、request_id与时间，不存原始名称/描述/原因、凭据或请求体。提交后关系型日志投影使用固定EventID唯一约束防重，失败留pending，通过有界入口恢复；只处理workspace_audit且不持业务事务锁。ClickHouse当前缺少同等唯一保证，本阶段不投影并保留pending，不据关系库结果宣称CH投影已验证。尚未实现后台通用outbox worker，未投递事实不清理。

## 9. 留存、归档与删除

运行元数据、事件内容、文件、版本、幂等记录与费用关联分别管理保留期，具体默认值按计划 §5.17；部署调整只改变未来清理策略，不能静默立即删除历史数据。

文件删除先在数据库标记 `deleting` 和持久化删除任务，在事务外删对象，确认后标记 `deleted`。发布引用、审批、检查点、核账和 `retention_hold` 均阻止提前清理；检查失败或引用状态不确定时保留并告警。

Workspace 退出按“停止触发 → 禁止新任务 → 处理活跃任务 → 撤销凭据 → 确认导出与留存 → 归档 → 异步清内容”执行。运行内容删除不得级联抹去费用或必要审计，也不能为保留账务而无限保存原始用户文档。

## 10. 交付检查

涉及数据行为的变更须实际验证事务回滚、唯一冲突、版本竞争、跨租户引用、旧 epoch、重复事件、零值/NULL、int64 与 UTF-8 边界及必要恢复路径；根据影响范围执行真实数据库矩阵，不以 mock 或编译替代。

验证要求与证据存放见 [测试与验收](07-acceptance.md)。测试源码和夹具仅本地保存；详细报告、SQL 输出、数据库备份、凭据及日志不提交，提交正文只记录实际验证摘要和未验证范围。迁移、正式模型、契约、配置和必要文档仍按 [Git 规范](08-git-commit.md) 同步交付。
