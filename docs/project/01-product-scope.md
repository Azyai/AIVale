# 01 产品范围与用户流程规范

## 1. 定位与使用边界

AIVale 在现有模型网关内增加智能体开发、Skills、MCP 接入、运行调度与治理。客户使用同一控制台、账号、模型 Token 和账务体系，完成模型调用与智能体开发。

本规范依据已确认开发计划第 1–4、9 章，约束后续实现，不代替计划中的任务依赖、接口清单或验收门禁。除第 2 节明确列出的代码事实外，下文的 Workspace、Agent 发布与 Run 流程均是待按阶段交付的目标，不能作为当前可用功能宣传。

- 保持同仓库模块化单体：现有 Gin 服务承载控制面和模型网关，同仓库 worker 承载执行编排，客户脚本进入独立隔离环境。
- 原生运行路线为 Go + Eino；平台保有状态、权限、事件和计量契约，不对外暴露框架内部对象。
- 保留现有 Dify/Coze 调用适配，不整体合并其控制台，也不把调用适配等同于原生 Agent 开发平台。
- 初期复用业务数据库、Redis、Team、User、Token、钱包、订阅和前端基础设施，不重建一套平行账号或账务系统。

## 2. 当前代码已提供什么

| 已有内容 | 代码或契约位置 | 准确含义 |
| --- | --- | --- |
| Agent 最小公共契约 | `.agents/agent-platform/contracts/v1/` | 冻结类型、样例与接口形状，不代表对应业务 API 已上线 |
| 五项功能开关 | `setting/agent_setting/config.go` | 默认关闭，使用现有 Option 配置；配置开启不等于能力就绪 |
| 新命名空间准入 gate | `middleware/agent_platform.go` | 控制新请求准入，不代替身份认证、租户授权或运行取消 |
| 内部作用域与请求上下文 | `model/agent_scope.go`、`service/agent/context.go` | 仅元数据载体；`AgentScope` 不是数据库表，也不能证明访问已授权 |
| 公开全局能力探测 | `router/agent-router.go`、`controller/agent_platform.go`、`service/agent/capabilities.go` | 只读有效开关，当前 `runtime_ready` 固定为 `false` |

精确 `GET /api/agent-platform/capabilities` 是当前已注册的探测入口，位于现有 API 中间件链内。它不读取租户数据、不调用模型、不初始化执行引擎，也不接受客户端声明的 Team/Workspace 作用域。

响应保留 `success/code/message/request_id/data`，成功 `code=OK`；`data` 包含 `schema_version=1`、五项有效布尔开关与 `runtime_ready`，响应使用 `Cache-Control: no-store`。总开关关闭时该精确 GET 仍可读取禁用配置；HEAD、写方法和子路径不享有这项探测豁免。

| 配置键 | 有效条件 |
| --- | --- |
| `agent_setting.enabled` | 自身为精确有效的开启值 |
| `agent_setting.worker_enabled` | 总开关与 worker 开关均开启 |
| `agent_setting.mcp_enabled` | 总开关与 MCP 开关均开启 |
| `agent_setting.skills_enabled` | 总开关与 Skills 开关均开启 |
| `agent_setting.scripts_enabled` | 总开关、Skills 与脚本开关均开启 |

`GET /api/status` 的 `data.agent_platform` 也只表达有效配置。不得据此显示 worker 在线或已完成客户准入。开启所有开关不会创建尚未实现的 Workspace、Run、审批、MCP 或脚本处理器；公开探测不替代未来的工作区权限探测。

## 3. 租户、身份与资源

| 概念 | 产品规则 |
| --- | --- |
| Team | 租户与账务主体；首期沿用一个用户最多属于一个 Team 的成员体系 |
| Workspace | 属于一个 Team；成员是 Team 成员子集，同 Team 的不同工作区仍需分别授权 |
| Agent | 可持续编辑的稳定资源身份，草稿与已发布版本分离 |
| AgentVersion | 已发布的不可变执行配置，固定模型策略、依赖版本和输入输出契约 |
| Run | 一次持久化执行，绑定工作区、版本、输入、发起人、预算和费用引用 |
| Worker | 执行服务身份，不等同发起用户，不获得父模型 Token 明文 |

工作区角色为 `admin`、`developer`、`operator`、`viewer`，动作权限按计划权限矩阵实施。Team owner 继承工作区 admin；其他成员通过显式工作区成员记录确定角色，不能因为属于同一 Team 就默认可访问全部资源。

浏览器管理沿用现有用户会话；新增写接口按凭据来源核对 CSRF/Origin 防线，不假设所有旧管理接口已统一覆盖。公开运行使用模型 Token，并要求独立 Agent grant；旧模型 Key 不自动拥有 Agent 权限。PAT 与模型 Token 是不同机制，现有 PAT 管理 scope 不自动转换为 Agent grant。

公开 Token scope 使用 `agent:run`、`run:read`、`run:cancel`、`artifact:read`；管理动作 `run:create` 是另一层权限。看到 Run 元数据不自动取得输入输出、产物下载或费用明细读取权。

有效权限取平台政策、Team 成员状态、Workspace 角色、资源、Token grant、发布配置与工具/凭据策略的交集。历史快照不覆盖实时撤销；平台管理员跨客户操作走有审计的运营入口。

个人用户可继续使用原模型平台，首期 Agent 功能要求先有 Team。不得静默创建个人 Workspace，或在团队资金不足时切换到个人钱包。具体授权边界见 [安全与权限规范](06-security-and-permissions.md)。

## 4. 客户的主流程

以下为按阶段实现后的主流程，不能通过静态页面、假数据或仅开启开关声明已交付。

1. 用户进入已授权工作区，明确当前 Team、可用资源和自身权限。
2. 创建 Agent 草稿，填写模型策略、指令、输入输出约束与默认预算；编辑带修订号，冲突时保留未保存内容。
3. 根据已开放阶段绑定固定 Skill 版本和 MCP 工具快照；发现工具不等于获准执行。
4. 调试时生成不可变调试快照并创建 `mode=debug` 的 Run，明确资金 Token、预算及真实费用。
5. 发布前验证模型、依赖、工具 Schema、权限与预算，创建新的不可变版本，原子切换发布指针。
6. 浏览器运行明确选择当前 Team 内有权使用的资金 Token；公开请求的资金 Token 必须是实际认证的 caller Token。
7. 创建请求通过鉴权、输入校验及幂等检查后持久化受理，返回 Run 身份，页面显示真实排队与执行状态。
8. 通过持久化事件查看过程；需要审批时展示实际动作、参数摘要、风险和有效期，不在批准前执行远端副作用。
9. 用户读取授权结果、产物与实际费用；失败说明原因和恢复方式，未知外部结果先核查。
10. 取消停止后续动作，不承诺撤销已发生外部操作或退还全部模型消耗；重试终态任务需要明确创建新 Run。

运行状态、事件、预算与恢复细节见 [Agent 运行规范](02-agent-runtime.md)。接口路径、字段及错误码以计划和正式契约为准，不在本规范另建一套 API。

## 5. 页面与操作表达

- 已授权工作区是资源操作上下文。切换工作区、团队或退出登录时，取消旧订阅并清理相关敏感缓存，不能串用查询结果。
- 未就绪能力应展示准确原因；全局开关、运行时就绪、工作区权限与资源状态必须分别判断。
- 草稿、发布版本与实际运行版本要能区分；保存草稿不会更新已发布版本，也不会改变运行中的配置。
- 运行详情展示当前步骤、等待原因、可执行动作和费用状态；断开事件流不等于任务失败，费用待核对不等于零费用。
- 输入、提示词和结果正文不放进普通列表或悬浮提示；内容查看与下载按独立权限控制。
- 错误说明发生了什么、输入是否保留及下一步可做什么；未知结果场景不提供普通用户强制成功、补扣或盲目重发按钮。

## 6. 阶段交付边界

| 层次 | 计划范围 | 允许开放的能力与边界 |
| --- | --- | --- |
| L0 内部工程验证 | P00–P03 | 工作区、Agent 版本、单模型运行、事件及基础预算；仅开发和指定内部账户 |
| L1 受控客户试用 | P04–P06 | 受控远程只读 MCP、指令类 Skills、可靠运行、审批恢复与核账；仅受邀客户和审核资源 |
| L2 任务与文件自动化 | P07–P08 | 持久化触发、隔离脚本和授权产物；先满足风险策略、配额与执行隔离 |
| L3 完整开发工作台 | P09–P10 | 固定 DAG 画布、有限多 Agent、受控检索、评测和模板复制 |
| L4 正式商业发布 | P11 | 容量、备份恢复、灰度、审计、留存和运营交接完成后按策略放量 |

L1 可形成受控收费产品，但必须具备相应授权、计费对账和事故处理能力。适用于已开放能力的 P11 上线检查不能因为阶段编号靠后而延期；L3 全部完成也不是 L1 的前提。

首个纯文本闭环使用 `kind=single`、文本输入输出和空 Skill/Tool 绑定。conversation、workflow、Skills、MCP、脚本、产物及子 Agent 按依赖逐步实现，不通过预填假字段宣称首批已支持。

## 7. 不纳入首期默认承诺

- 公共技能市场交易分成、多组织成员体系、完整自建向量数据库和 GPU 调度。
- 任意客户镜像、宿主命令、任意内网 MCP 地址或不受限的出站网络。
- 模型自由创建无限子 Agent、动态无限循环、无界并行和跨工作区猜测 ID 复用资源。
- 用 Chat Completions 完整表达审批、长任务与恢复，或承诺所有模型协议的 Agent 能力完全等价。
- MCP OAuth、stdio 和将 AIVale 发布为 MCP Server；这些是现有 108 项任务之外的独立增量，不能混为一个已完成的 MCP 开关。
- 整体改写 relay、重命名全部旧表、替换登录体系、把维护系统任务锁当作客户 Run 队列，或为新增 Agent 先拆分全部微服务。

## 8. 变更与验收

每批从计划任务和依赖出发，描述实际启用能力及限制。范围变化先同步共同契约，再安排上下游实现；不复用已完成任务编号表示另一项能力。

适用规范见 [架构规范](04-architecture.md)、[数据库规范](05-database.md) 与 [测试和验收规范](07-acceptance.md)。本规范不降低计划的数据库、权限、计费和运行门禁，也不因报告退出 Git 而取消验证。
