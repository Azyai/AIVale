# 07 测试与验收规范

## 1. 完成条件

验收沿用已确认开发计划中的任务编号、依赖、阶段出口与门禁，不另造一套完成标准。每项验证必须说明前置条件、操作、可观察结果及失败路径；涉及权限、账务、并发或持久化时，检查对应数据和审计事实，不能只以页面正常或代码可编译判定完成。

测试源码、测试专用资源与夹具仅在本地保存和执行，不进入 Git；包括 Go 的 `*_test.go`、前端 `*.test.*` / `*.spec.*` / `__tests__/`、E2E、脚本测试及专用测试数据。公开契约样例、生产资源和构建元数据不因被测试引用而归入此范围，详见 [仓库内容管理](09-repository-hygiene.md)。

## 2. 按变更选择验证

| 变更 | 必须关注的行为 |
| --- | --- |
| API、权限、租户资源 | 请求响应契约、未登录、无权限、跨租户、无效输入与错误状态 |
| 数据库、迁移、事务 | 真实适用数据库的空库与旧库升级、重启幂等、数据保留、唯一约束及事务回滚 |
| 运行调度与外部调用 | 重复请求、竞争领取、超时取消、故障恢复及未知结果的处理 |
| 预算与账务 | 费用来源、额度边界、重复结算、失败退款及账本一致性 |
| 前端行为 | 类型检查、受影响文件 lint、加载/空/错态、权限、键盘与响应式 |
| 契约或独立模块 | 使用方兼容、固定样例、模块独立构建及对应回归 |

数据库验证范围逐任务遵守开发计划和明确的用户约定；P00-T03 的 MySQL 范围不能外推为其他数据库或其他版本已通过。生产源码及模块独立性要求仍按适用开发规则执行。

## 3. 构建与测试入口

命令以工程实际脚本和模块为准。根 Go 程序嵌入 `web/dist`，应先在 `new-api/web` 安装锁定依赖并构建前端；不能因缺少嵌入文件而改用空目录或占位页面伪造构建。

| 工作目录 | 命令与用途 |
| --- | --- |
| `new-api/web` | `bun install --frozen-lockfile`、`bun run typecheck`、`bun run build`：依赖、类型和构建 |
| `new-api` | `go build ./...`、`go vet ./...`：根模块编译与静态检查 |
| `new-api/relaykit`、`new-api/tokenkit` | 分别在 `GOWORK=off` 环境下运行 `go build ./...`、`go vet ./...`，不能用根模块成功替代 |
| 具备本地用例的 Go 模块 | `go test -count=1 ./...`，开发时可先按受影响包缩小范围 |
| 具备本地用例的 `new-api/web` | `bun run test`；同时按适用前端规则检查 lint 和交互行为 |

公共 CI 只承担构建、`go vet` 和前端类型检查，不宣称执行了未随仓库分发的测试。新克隆、CI 的构建成功、`[no test files]` 或零项测试均不等于验收通过。需要本地用例的验证，必须先确认源码、夹具与环境齐全；缺失时标明未验证，不用跳过测试、空脚本或 `passWithNoTests` 代替门禁。

## 4. 证据与交付

- 交付说明或获得授权的提交正文记录任务编号、实际命令、环境版本、覆盖范围、通过/失败/跳过数量，以及未运行项和原因。只写实际结果，不编造数量或完成状态。
- 详细验收报告、日志、截图、覆盖率、性能数据与测试输出仅存放于已被 `.gitignore` 忽略的本地目录；不提交原文件、压缩副本、截图副本或转写后的报告。
- 正式验收规则、API/Schema 契约和可公开的脱敏示例继续版本管理；与某次执行绑定的报告和结果不能改名成规范继续提交。
- 计划中的旧报告路径只作为历史引用，不再维护对应报告。完成记录使用本节的验证摘要方式，不修改已确认计划的业务内容来适应目录清理。
- 清理产物不撤销质量要求。存在未满足的权限、数据、计费或运行恢复门禁时，明确说明阻碍与可交付范围，不标为验收完成。

提交规则见 [Git 提交规范](08-git-commit.md)。
