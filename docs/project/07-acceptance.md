# 07 测试与验收规范

## 1. 完成条件

验收沿用已确认开发计划中的任务编号、依赖、阶段出口与门禁，不另造一套完成标准。每项验证必须说明前置条件、操作、可观察结果及失败路径；涉及权限、账务、并发或持久化时，检查对应数据和审计事实，不能只以页面正常或代码可编译判定完成。

测试源码、测试专用资源与夹具仅在本地保存和执行，不进入 Git；包括 Go 的 `*_test.go`、前端 `*.test.*` / `*.spec.*` / `__tests__/`、E2E、脚本测试及专用测试数据。公开契约样例、生产资源和构建元数据不因被测试引用而归入此范围，详见 [仓库内容管理](09-repository-hygiene.md)。

## 2. 按变更选择验证

| 变更 | 必须关注的行为 |
| --- | --- |
| API、权限、租户资源 | 请求响应契约、未登录、无权限、跨租户、无效输入与错误状态 |
| 数据库、迁移、事务 | 真实适用数据库的空库与旧库升级、重启幂等、数据保留、唯一约束及事务回滚 |
| 运行调度与外部调用 | 重复请求、竞争领取、超时取消、故障恢复及未知结果的处理 |
| 预算与账务 | 费用来源、额度边界、重复结算、失败退款及账本一致性 |
| 前端行为 | 类型检查、受影响文件 lint、加载/空/错态、权限、键盘与响应式 |
| 契约或独立模块 | 使用方兼容、固定样例、模块独立构建及对应回归 |

数据库验证范围逐任务遵守开发计划和明确的用户约定；P00-T03 的 MySQL 范围不能外推为其他数据库或其他版本已通过。生产源码及模块独立性要求仍按适用开发规则执行。

## 3. 构建与测试入口

命令以工程实际脚本和模块为准。根 Go 程序嵌入 `web/dist`，应先在 `new-api/web` 安装锁定依赖并构建前端；不能因缺少嵌入文件而改用空目录或占位页面伪造构建。

| 工作目录 | 命令与用途 |
| --- | --- |
| `new-api/web` | `bun install --frozen-lockfile`、`bun run typecheck`、`bun run build`：依赖、类型和构建 |
| `new-api` | `go build ./...`、`go vet ./...`：根模块编译与静态检查 |
| `new-api/relaykit`、`new-api/tokenkit` | 分别在 `GOWORK=off` 环境下运行 `go build ./...`、`go vet ./...`，不能用根模块成功替代 |
| 具备本地用例的 Go 模块 | `go test -count=1 ./...`，开发时可先按受影响包缩小范围 |
| 具备本地用例的 `new-api/web` | `bun run test`；同时按适用前端规则检查 lint 和交互行为 |

公共 CI 只承担构建、`go vet` 和前端类型检查，不宣称执行了未随仓库分发的测试。新克隆、CI 的构建成功、`[no test files]` 或零项测试均不等于验收通过。需要本地用例的验证，必须先确认源码、夹具与环境齐全；缺失时标明未验证，不用跳过测试、空脚本或 `passWithNoTests` 代替门禁。

## 4. 证据与交付

- 交付说明或获得授权的提交正文记录任务编号、实际命令、环境版本、覆盖范围、通过/失败/跳过数量，以及未运行项和原因。只写实际结果，不编造数量或完成状态。
- 详细验收报告、日志、截图、覆盖率、性能数据与测试输出仅存放于已被 `.gitignore` 忽略的本地目录；不提交原文件、压缩副本、截图副本或转写后的报告。
- 正式验收规则、API/Schema 契约和可公开的脱敏示例继续版本管理；与某次执行绑定的报告和结果不能改名成规范继续提交。
- 计划中的旧报告路径只作为历史引用，不再维护对应报告。完成记录使用本节的验证摘要方式，不修改已确认计划的业务内容来适应目录清理。
- 清理产物不撤销质量要求。存在未满足的权限、数据、计费或运行恢复门禁时，明确说明阻碍与可交付范围，不标为验收完成。

提交规则见 [Git 提交规范](08-git-commit.md)。

## 5. P00基础交付门禁

固定入口为 `.agents/agent-platform/delivery/gate.py`，命令和必需本地用例由同目录 `checks.json` 管理，操作及限制见该目录 README；空白 `batch-template.md` 只复制到忽略目录填写，不提交执行报告。

`build` 模式只证明锁定依赖下的构建、类型、vet、模块及差异检查，结果保持 `acceptance=not_run`。`foundation` 在此基础上实际执行所选P00回归，必须核对每个指定Go测试及前端文件；缺本地源码、零用例、跳过、重复/不完整报告、超时或命令失败均不能验收通过。首个失败阻断后续检查，输入在执行中变化也必须重新验证。新克隆/公共CI不含本地用例，不改变本规范的能力边界。

基准必须覆盖本批已提交、已暂存、工作区和未跟踪改动。基础配置对Go、模块元数据、SQL、迁移及数据库/部署配置采取保守范围判断；缺适用真实三库执行器时标记未完成，不提供关闭判定的参数或手填旧报告豁免。P00-T03的MySQL约定不适用于新的schema变更。无数据库影响的批次只能标为不适用。

结果和日志每次写入唯一的本地忽略目录；工具、固定配置和空白模板可跟踪，行为测试和填好的记录仍仅本地保留。`foundation`的结论限定为所选工程基础，不自动关闭P00-T01的历史全量失败，也不代替后续领域或正式发布验收。

## 6. 工作区数据库门禁

P01-T01使用同一入口的`--profile workspace`，在基础21项之后强制执行SQLite/MySQL/PostgreSQL三项真实隔离验证。固定配置限制任务ID和支持的数据库影响路径，未知模型或驱动变更不能沿用该配置放行；扩展前先补相应真实检查。

每个引擎包含fresh/upgrade各独立主库和日志库，真实启动入口首次运行及两次连接关闭后重启；核对完整结构/数据稳定、两表只在主库、索引定义、原生重复键错误、Team范围、父级/成员引用及事务回滚。升级用例明确区分rc.42发布最小投影与开发前Team投影，不声称完整发布备份。该验证不等于数据库服务崩溃恢复或应用全进程重启。

门禁读取本次新目录中的原始Go事件，重组长日志分片后核对唯一场景摘要和收据，缺任一引擎、场景、启动轮次、成功事件或正常关闭均不能通过；关闭命令非零即使状态写stopped也不通过。结果只能覆盖实际版本和P01-T01持久化范围，不证明P01-T02角色鉴权、最低版本或全量历史基线通过。

## 7. 工作区访问门禁

P01-T02使用`--profile workspace-access`：基础21项、管理会话到工作区guard的真实HTTP适配用例、三库两阶段验证，共25项。固定配置只允许本批三个model/service/middleware文件的数据库影响范围；原P01-T01收据没有访问阶段，不能代替此配置。

各引擎先保留新建/升级及重复启动的迁移验证，再在同一四目标上用独立服务测试进程验证fresh/upgrade各96个角色动作组合和范围、owner双事实、跨租户/工作区、默认角色与root无豁免、实时降权/退组/停用/软删除、会话状态/版本/到期、归档/暂停、上下文/数据库错误及无泄露响应；访问夹具不得修改上一阶段已有数据。

适配用例必须经过现有UserAuth，另覆盖PAT/模型Token/伪通用上下文拒绝、请求Team不能覆盖、规范路径ID、失败不绑定Scope、旧结果清理和下一次受控调用重新判定。代码没有客户CRUD路由时，仅证明可复用guard及内部访问服务，不以测试路由宣称业务API开放。

两阶段退出码、原始Go事件、完整且唯一的场景摘要、同一引擎版本及正常关闭须全部匹配；缺访问阶段/场景、跳过、矩阵未执行、固定负例未通过或收据不一致均阻断。历史P00-T01开放项仍单列，所选门禁成功不关闭未运行的全量基线。

## 8. 工作区只读API门禁

P01-T03使用`--profile workspace-read`：基础21项、既有管理会话工作区guard适配1项、SQLite/MySQL/PostgreSQL三项真实验证，共25项。各引擎通过`database/matrix.py --read`在同一组四个标记隔离目标上顺序执行T01迁移、T02访问判定、T03只读HTTP；三个阶段均保留fresh/upgrade，缺前一阶段、用旧收据替代或只执行SQLite均不得验收。

HTTP阶段必须通过生产`SetApiRouter`注册和现有`UserAuth`，验证两个GET的默认关闭开关、仅管理会话、PAT/模型Token拒绝、跨租户/同Team隔离、owner双事实与显式成员、角色/状态权限摘要、授权和筛选先于COUNT/分页、稳定排序/空页、字面且区分大小写搜索、查询/ID边界及实时撤销。SID、状态和角色的大小写/尾空格差异、账号/会话失效、数据库/Context失败、白名单与安全数值边界、固定安全错误及`no-store`均应有负例。

公开Schema应在禁网络解析条件下校验示例与实际列表/详情/错误响应，并通过反例证明额外秘密/策略字段、缺字段、坏ID和不安全数字被拒绝。HTTP请求数量实际累计；固定摘要、同次运行ID、引擎版本、原始测试事件、退出码和正常清理必须匹配，不能用手写成功标记替代断言。测试夹具仅改本阶段自有行，保留前两阶段的数据与日志库隔离。

本节定义适用门禁，不记录或声明任何一次最终验证完成。所选25项通过也不能关闭P00-T01历史全量基线或既有PAT全量路由catalog中的14项不一致；这些开放项仍须单独修复并重新验证。结果仅覆盖实际引擎/版本，不外推为最低兼容版本、生产部署或完整客户工作台通过。


## 9. 工作区写生命周期门禁

P01-T04使用workspace-write配置，共25项：基础21项、管理会话适配1项、真实三库各1项。每个引擎在同四隔离目标上顺序执行迁移、访问判定、只读HTTP、写生命周期四阶段；write隐含read/access，不用旧收据或单库结果代替。

新两表必须只在主库，fresh/upgrade各证明索引及唯一约束、三次连接启动后的schema/数据保留；真实生产路由覆盖owner创建/初始管理员原子性、各角色/跨租户、幂等scope/同请求重放/异请求冲突/撤权/过期保留、revision与并发竞争、归档活动计数和未来依赖保护、严格输入、DTO与公开Schema。故障注入验证管理员/业务/幂等/审计任一失败不产生半完成事实；日志投影故障保留pending并可幂等恢复，审计不得含原始正文或凭据。另验证认证/授权/输入拒绝有正确失败事件、主体与request_id，未知主体不伪造身份，成功写入和GET不重复生成拒绝审计；日志库故障不得改变已拒绝请求为成功。

每个场景要求29项行为布尔值全为true、startup_passes精确整数3、实际HTTP请求数精确正整数；四阶段各自退出码、原始Go事件、唯一摘要、同运行编号/版本及正常关闭全部匹配。不能把固定成功标记代替真实断言或把未执行/跳过记绿。当前归档只证明运行资源接入前保护，不宣称Run排空/停止计划/历史Run接口或ClickHouse投影通过；历史全量与PAT目录开放项继续单列。
